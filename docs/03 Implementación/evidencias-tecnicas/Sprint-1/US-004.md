## Cliente documental y persistencia mínima

| Atributo documental | Tipo/restricción | Uso en US-004 |
|---|---|---|
| cliente_id | UUID, PK, generado | Generado por PostgreSQL |
| nombre | VARCHAR(150), NOT NULL | Capturado, obligatorio, no vacío tras trim |
| telefono | VARCHAR(30), NULL | Columna nullable; no se captura |
| email | VARCHAR(255), NULL | Columna nullable; no se captura |
| direccion | VARCHAR(255), NOT NULL | Capturada, obligatoria, no vacía tras trim |
| referencia | VARCHAR(255), NULL | Columna nullable; no se captura |
| latitud | NUMERIC(9,6), NOT NULL, -90…90 | Capturada, número finito, hasta 6 decimales |
| longitud | NUMERIC(9,6), NOT NULL, -180…180 | Capturada, número finito, hasta 6 decimales |
| estado | VARCHAR(20), NOT NULL, default ACTIVO | Asignado por servidor, no seleccionable |

El formulario utiliza exclusivamente nombre, dirección, latitud y longitud. No añade DNI, teléfono obligatorio, costos ni otros datos. Los campos opcionales documentados se conservan nullable en el modelo, pero no se incluyen en el request del incremento. No se implementó preferencias_cliente, catálogo, búsqueda, edición o eliminación de clientes.

Cada registro válido crea un Cliente mínimo; dentro de la misma transacción su cliente_id generado se asigna al Pedido. Al insertar Pedido, Cliente ya existe en esa transacción y PostgreSQL valida la FK. No se acepta un cliente_id arbitrario del navegador ni se inventa una política de deduplicación/reutilización de clientes.

## Pedido y validaciones

| Campo persistido | Fuente/validación | Entrada del usuario |
|---|---|---|
| pedido_id | Modelo SQL 7.8: UUID generado | No |
| cliente_id | Modelo SQL 7.8: UUID NOT NULL, FK a Cliente | Generado a partir del cliente capturado |
| peso_kg | NUMERIC(10,2), > 0 | Sí, obligatorio |
| volumen_m3 | NUMERIC(10,3), > 0 | Sí, obligatorio |
| ventana_inicio | TIMESTAMPTZ, NOT NULL | Sí, obligatoria |
| ventana_fin | TIMESTAMPTZ, NOT NULL, > inicio | Sí, obligatoria |
| prioridad | EXPRESS / ESTANDAR / ECONOMICO | Sí, obligatoria |
| tipo_producto | PERECEDERO / NO_PERECEDERO | Sí, obligatorio |
| estado | Default documental PENDIENTE | No |
| creado_en | Default CURRENT_TIMESTAMP | No |

Los máximos 99,999,999.99 kg y 9,999,999.999 m³ y los mínimos representables 0.01/0.001 se derivan de precisión/escala NUMERIC y >0: no son límites logísticos nuevos. No se redondean silenciosamente entradas con exceso de decimales. Se rechazan strings en campos numéricos, null/ausencia, texto vacío, valores fuera de rango, campos no autorizados y enumeraciones inválidas. UUID y fechas de creación se generan en PostgreSQL.

La precisión se valida considerando también el exponente de un número JSON: coordenadas como 1e-7 se rechazan con 400 en lugar de provocar un error interno del validador de decimales instalado. Se cubrieron NaN/Infinity en unitarias, límites representables y números en notación científica en unitarias e integración.

La API exige ISO 8601 con Z o desplazamiento horario; valida fechas reales y fin estrictamente posterior al inicio antes de crear Cliente. La interfaz utiliza datetime-local, indica la zona del navegador y convierte a ISO UTC antes de enviar. No se inventó una regla que prohíba fechas pasadas. La ventana se persiste como TIMESTAMPTZ. Las respuestas serializan Decimal como cadena para conservar precisión.

## API, autorización y sesión

Único endpoint nuevo: **POST /orders**. JSON request:

```json
{
  "cliente": { "nombre": "Cliente de prueba", "direccion": "Destino de prueba", "latitud": -12.065, "longitud": -75.204 },
  "peso_kg": 2.5,
  "volumen_m3": 0.015,
  "ventana_inicio": "2026-10-02T09:00:00-05:00",
  "ventana_fin": "2026-10-02T11:00:00-05:00",
  "prioridad": "ESTANDAR",
  "tipo_producto": "NO_PERECEDERO"
}
```

201 devuelve los diez campos de Pedido, incluyendo ambos UUID generados, estado PENDIENTE y creado_en; no devuelve datos del cliente, contraseñas o hashes. 400: datos inválidos/no permitidos; 401: sesión ausente, inválida, expirada o usuario deshabilitado; 403: rol no autorizado/origen ajeno. Swagger en http://localhost:3000/api/docs documenta request, respuesta 201, 400/401/403, Bearer y cookie. /orders no tiene GET/PATCH/DELETE; tampoco se creó /clients.

OrderRegistrationGuard se aplica después de JwtAuthGuard y mantiene RequestOriginGuard. No se modificó AdministratorGuard ni autorización de Usuarios. Cookie distrirapido_session_v2 conserva HttpOnly, SameSite=Lax, Path=/, Secure en producción/HTTPS y caducidad existente. GET /auth/me y POST /auth/logout permanecen.

## Interfaz y borrador

Ruta /pedidos/nuevo; enlaces Registrar pedido en acceso de Administrador/Operador y navegación correspondiente. El Administrador conserva Usuarios; el Operador no obtiene acceso a Usuarios. No se añadió Consultar pedidos.

OrderForm usa estado local en memoria. La revalidación de sesión al recuperar foco mantiene la ruta montada mediante la corrección previa de ProtectedRoute. F5 conserva la sesión, pero puede limpiar el borrador. Logout desmonta el formulario. No se guarda borrador, JWT ni datos sensibles en localStorage/sessionStorage/cookies/IndexedDB/URL.

Se muestran errores de campos, carga, errores de API y confirmación con código del pedido. Los datos se conservan al fallar el registro. Mientras la petición está pendiente, un ref bloquea el segundo submit sin depender del siguiente render; botón/controles quedan deshabilitados. Después del éxito no existe botón para reenviar la misma operación; Registrar otro pedido inicia un formulario limpio. No se implementó idempotencia para reintentos independientes tras un fallo de red ambiguo.

## Prueba manual exacta

1. Mantener el PostgreSQL existente en localhost:5433. La migración ya quedó aplicada: no ejecutar bootstrap ni recrear base. Backend actualizado en http://localhost:3000; frontend en http://localhost:5173. Si las terminales se cerraron, ejecutar desde backend `npm run start:dev` y desde frontend `npm run dev`. Si npm global falla: `node "$env:ProgramFiles\nodejs\node_modules\npm\bin\npm-cli.js" run start:dev` / `run dev`, respectivamente. No iniciar una segunda instancia sobre un puerto ocupado.
2. Abrir http://localhost:5173/login e ingresar con admin@distrirapido.local y su contraseña actual. Comprobar Usuarios y roles antes de continuar. No cambiar el rol del administrador.
3. Pulsar Registrar pedido; URL /pedidos/nuevo. Enviar vacío: errores de campos y primer campo enfocado; ningún registro.
4. Completar Nombre del cliente `Prueba manual US-004`, Dirección `Destino de prueba en Huancayo`, Latitud `-12.065`, Longitud `-75.204`, Peso `2.5`, Volumen `0.015`, Inicio `02/10/2026 09:00`, Fin `02/10/2026 11:00`, Prioridad Estándar y Tipo de producto No perecedero. El horario se interpreta en la zona local indicada por la interfaz. No se prohíben fechas pasadas por una regla inexistente.
5. Antes de guardar, cambiar de pestaña/aplicación y regresar: conservar todos los datos. Probar fin anterior al inicio, latitud 91, peso cero o exceso de decimales: deben rechazarse. Corregir los valores.
6. Pulsar Registrar pedido. Mientras está pendiente, el botón queda deshabilitado. Debe aparecer Pedido registrado correctamente, código UUID y estado Pendiente. En Network, POST /orders = 201; payload no tiene pedido_id/estado/creado_en. No hay pantalla Consultar pedidos.
7. Pulsar Registrar otro pedido: formulario limpio. Completar parte y presionar F5: sesión vigente conservada, borrador puede limpiarse.
8. Cerrar sesión: vuelve a login. Abrir directamente /pedidos/nuevo, /usuarios y /acceso/administrador: login. La cookie v2 se elimina.
9. Ingresar con operador.prueba@distrirapido.local y su contraseña actual: Registrar pedido disponible y mismo flujo permitido. Usuarios no debe estar disponible. No se cambió su contraseña.
10. Con una cuenta ACTIVO de Conductor o Auditor: no debe aparecer Registrar pedido y acceso directo se redirige a su área permitida; POST /orders con su sesión devuelve 403. Sin sesión devuelve 401. No usar el administrador principal para probar cambios de rol.
11. En http://localhost:3000/api/docs confirmar únicamente POST /orders, schema CreateOrderDto y respuestas documentadas. No publicar tokens o credenciales.

US-004 queda implementada y verificada automáticamente. Esperar validación manual y autorización explícita antes de US-005.
