## Endpoints y reglas

| Endpoint | Resultado |
|---|---|
| GET /users | 200, lista de cuentas con email, rol, estado y datos mínimos del modelo. |
| GET /users/:id | 200, cuenta pública; UUID inválido 400, ausencia 404. |
| POST /users | 201; email válido/normalizado, contraseña inicial, rol existente permitido y estado opcional (ACTIVO por defecto). |
| PATCH /users/:id | 200; únicamente email, rol_id, estado; PATCH vacío 400. Contraseña y propiedades extra rechazadas. |
| GET /roles | 200; roles existentes pertenecientes a los cuatro nombres de línea base. Sin creación/edición de roles. |

Todos requieren sesión JWT válida por cookie o Bearer, cuenta ACTIVO y rol vigente Administrador. 401 sin autenticación; 403 con cuenta autenticada sin autorización. Cambiar el rol en base afecta la siguiente petición aunque el JWT siga vigente. GET /roles también es exclusivo de administración.

Estados limitados a ACTIVO, INACTIVO, BLOQUEADO, validados por DTO y CHECK existente. El rol debe existir y estar permitido. Duplicado de email devuelve 409 comprensible; email se normaliza a minúsculas sin espacios externos. UNIQUE/FK continúan en PostgreSQL. Las respuestas públicas utilizan select explícito de Prisma, sin password_hash, contraseñas ni JWT. No se registran credenciales en logs. Los errores inesperados continúan sanitizados por el filtro existente.

POST/PATCH verifican Origin y Fetch Metadata; CORS mantiene el origen explícito, credenciales y añade PATCH. El límite de intentos de login continúa; las operaciones autenticadas de administración no consumen ese límite. No se añadieron dependencias.

## Cookie y regresión de autenticación

La cookie anterior `distrirapido_session`, Path=/auth, no podía acompañar /users ni /roles. La nueva `distrirapido_session_v2` usa Path=/, host-only, HttpOnly, SameSite=Lax y Secure en HTTPS/producción. Mantiene la vigencia del JWT.

Login elimina cookies antiguas y emite la nueva. GET /auth/me admite una cookie antigua válida y la migra: conserva exactamente el JWT y expiresAt; el maxAge corresponde al tiempo restante. Se eliminan las variantes antiguas /auth y /. Si llega la cookie nueva, /auth/me no reemite Set-Cookie; tampoco escribe cookie al consultar con Bearer. Así la comprobación normal no vuelve a guardar una cookie después de un logout concurrente. La nueva tiene precedencia y una nueva corrupta no recurre a la antigua.

Logout elimina la cookie nueva y las variantes antiguas. La regresión verifica login, /auth/me, restauración/F5, expiración, logout y rutas protegidas posteriores, además de migración antigua → /users sin renovar JWT. No se usa localStorage/sessionStorage para credenciales.

Se conserva la decisión de MVP de US-002: logout elimina la sesión del navegador; no revoca globalmente JWT Bearer exportados antes del cierre, que mantienen vigencia hasta expirar. No hay Redis ni tabla/lista de revocación.

## Prueba manual exacta

1. Mantener PostgreSQL Docker existente en 5433. No recrear contenedor/volumen, no borrar/recrear la base, no volver a ejecutar bootstrap ni modificar .env. US-003 no necesita migración.
2. Desde backend ejecutar `npm run start:dev`; si npm global falla, `node "$env:ProgramFiles\nodejs\node_modules\npm\bin\npm-cli.js" run start:dev`. Si queda un proceso iniciado con el comando antiguo, detener exclusivamente esa terminal de DistriRapido mediante Ctrl+C antes de iniciarlo. El comando actualizado observa `src` y reinicia automáticamente; cambios en `.env` requieren reinicio manual. Véase [corrección de la prueba manual](US-003-correccion.md).
3. Desde frontend mantener/iniciar `npm run dev` (mismo reemplazo de npm si es necesario). Abrir http://localhost:5173. Usar localhost también en VITE_API_URL/backend, evitando mezclar 127.0.0.1 con localhost.
4. Entrar con el Administrador existente. Una sesión previa vigente se migra al recargar. Desde /acceso/administrador pulsar “Usuarios y roles”.
5. En /usuarios comprobar correo, rol y estado. En móvil, deslizar horizontalmente la tabla para ver las demás columnas/Editar.
6. Pulsar “Crear usuario”. Intentar enviar vacío: se muestran validaciones. Introducir un email nuevo válido, contraseña inicial propia de 12–128 caracteres, rol permitido y ACTIVO. Guardar; debe aparecer en el listado. No usar datos ilustrativos de Stitch.
7. Intentar crear otro usuario con el mismo email: debe aparecer mensaje de correo duplicado. Cancelar.
8. En la cuenta nueva (no tu administrador), pulsar Editar; modificar email/rol/estado, guardar y comprobar cambios en el listado. No debe existir campo para cambiar contraseña. Probar INACTIVO/BLOQUEADO para deshabilitar y ACTIVO para habilitar.
9. Presionar F5 en /usuarios: continúa autenticado y muestra el listado.
10. Pulsar “Cerrar sesión”: vuelve a /login. Escribir directamente /usuarios o una URL de edición: vuelve a login. F5 tampoco restaura acceso tras logout.
11. Iniciar sesión con una cuenta ACTIVO de Operador / Técnico, Usuario Final / Conductor o Auditor Externo: no aparece acceso de administración; /usuarios lleva a su pantalla permitida. Llamar GET /users en Network/Swagger con su sesión/Bearer debe devolver 403. Sin sesión/Bearer: 401. No publicar tokens.
12. Swagger en http://localhost:3000/api/docs: confirmar endpoints de Usuarios/Roles y probar con autorización propia. Ninguna respuesta de /users debe contener password_hash. No modificar tu cuenta administradora para probar estados/roles; usa la cuenta nueva.
