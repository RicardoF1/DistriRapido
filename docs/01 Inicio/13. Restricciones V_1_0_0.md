# 2. Propósito

Este documento identifica y analiza las restricciones que pueden condicionar el desarrollo, implementación y operación de la plataforma web para la optimización sostenible de rutas de última milla en Huancayo.

El análisis considera cuatro dimensiones:

1. Salud y Seguridad Pública.
2. Costo del Ciclo de Vida (LCC).
3. Cero Carbono Neto y Sostenibilidad.
4. Aspectos Culturales, Sociales y Económicos.

Para cada dimensión se establece la restricción principal y una estrategia de mitigación o diseño que pueda incorporarse progresivamente a la solución.

# 4. Análisis de Impacto por Dimensión

## 4.1. Salud y Seguridad Pública

La plataforma manejará información que puede relacionarse con personas, pedidos, direcciones y ubicaciones geográficas. Por ello, el acceso no autorizado constituye una restricción relevante desde la etapa de diseño.

Las medidas consideradas son:

- Comunicación mediante HTTPS.
- TLS 1.3 para el transporte cuando la infraestructura lo permita.
- Protección de credenciales mediante hashes de contraseñas.
- Control de acceso basado en roles.
- Validación de datos de entrada.
- Registro de auditoría.
- No almacenar contraseñas en texto plano.
- Evitar incluir información sensible innecesaria en logs.

La seguridad se implementará principalmente en el backend **NestJS**, evitando que el frontend acceda directamente a PostgreSQL.

---

## 4.2. Análisis de Costo del Ciclo de Vida

El proyecto tiene una restricción presupuestaria debido a que será desarrollado y desplegado con recursos limitados.

La estrategia tecnológica busca disminuir costos mediante tecnologías de código abierto:

```text
React
   ↓
NestJS / Node.js
   ↓
Prisma
   ↓
PostgreSQL
```

Para el cálculo de costo del ciclo de vida se deben considerar:

- Hosting del frontend.
- Hosting del backend.
- Base de datos PostgreSQL.
- Dominio, si corresponde.
- Certificado HTTPS cuando no sea proporcionado por el hosting.
- Consumo del servicio de mapas/rutas.
- Mantenimiento.
- Copias de seguridad.
- Recursos de almacenamiento.

La arquitectura no debe incorporar servicios de pago innecesarios si existe una alternativa técnicamente suficiente para el alcance académico del proyecto.

---

## 4.3. Cero Carbono Neto y Sostenibilidad

La sostenibilidad se aborda en dos niveles.

### Nivel 1: Sostenibilidad de la operación logística

El producto busca apoyar la optimización de rutas considerando variables como:

- Distancia recorrida.
- Tiempo de recorrido.
- Consumo estimado de combustible.
- Emisiones estimadas de CO₂.
- Cumplimiento de ventanas horarias.

### Nivel 2: Sostenibilidad del software

El software deberá evitar procesamiento innecesario.

Se consideran como medidas:

- Consultas SQL optimizadas.
- Índices en consultas frecuentes.
- Ejecución controlada del Algoritmo Genético.
- Evitar cálculos duplicados.
- Uso eficiente de memoria.
- Procesamiento únicamente cuando sea requerido.

El proyecto no afirmará que la plataforma es de **cero carbono neto** por el solo hecho de optimizar rutas. El sistema podrá generar indicadores de sostenibilidad y apoyar la reducción estimada de consumo/emisiones de la operación logística.

---

## 4.4. Aspectos Culturales, Sociales y Económicos

La plataforma se desarrollará considerando el contexto local de **Huancayo**.

Entre las restricciones se consideran:

- Diferencias en disponibilidad de dispositivos.
- Diferencias en calidad de conexión a Internet.
- Uso predominante de dispositivos móviles para determinadas operaciones.
- Necesidad de interfaces comprensibles para usuarios con diferentes niveles de experiencia digital.
- Características de las direcciones y referencias utilizadas localmente.

Por esta razón, la solución considera:

```text
Aplicación Web Responsive
           +
Modo Conductor PWA
           +
Interfaz de lenguaje claro
           +
Tolerancia a conectividad intermitente
```

# 5. Restricciones Técnicas Derivadas

| ID | Restricción | Categoría | Severidad | Tratamiento |
|---|---|---|---|---|
| RT-001 | El frontend no accederá directamente a PostgreSQL. | Tecnología | Alta | Todas las operaciones pasarán por la API NestJS. |
| RT-002 | El sistema dependerá de la disponibilidad del servicio OSRM para obtener información vial. | Tecnología | Alta | Implementar manejo de errores y tiempos de espera en la integración. |
| RT-003 | La ejecución del Algoritmo Genético requiere recursos computacionales proporcionales al tamaño del problema. | Tecnología | Media-Alta | Establecer parámetros controlados de población, generaciones y criterio de parada. |
| RT-004 | La PWA depende de las capacidades disponibles en el navegador y dispositivo del conductor. | Tecnología | Media | Implementar progresivamente las funciones PWA necesarias para el alcance. |
| RT-005 | El despliegue debe ajustarse al presupuesto disponible para hosting. | Costo | Alta | Priorizar infraestructura de bajo costo y tecnologías open source. |
| RT-006 | La calidad de la solución de rutas depende de los datos proporcionados por el servicio de rutas. | Tecnología | Media-Alta | Validar respuestas de OSRM y manejar datos incompletos o errores. |

# 6. Restricciones Operativas

| ID | Restricción Operativa | Impacto | Mitigación |
|---|---|---|---|
| RO-001 | Los pedidos deben disponer de información mínima de ubicación para poder incorporarse al proceso de optimización. | Alto | Validar coordenadas y datos obligatorios antes de optimizar. |
| RO-002 | La disponibilidad de vehículos condiciona la solución generada. | Alto | Validar capacidad y estado de la flota antes de ejecutar el algoritmo. |
| RO-003 | La disponibilidad de conductores condiciona la asignación de rutas. | Alto | Validar conductores disponibles antes de confirmar la planificación. |
| RO-004 | Cambios operativos durante una ruta pueden volver obsoleta una solución previamente calculada. | Medio-Alto | Registrar eventos y permitir solicitar una nueva optimización cuando corresponda. |
| RO-005 | La conectividad puede variar durante la ejecución de una ruta. | Medio-Alto | Utilizar PWA y mecanismos de sincronización para las operaciones que lo requieran. |

# 7. Restricciones Económicas

El proyecto deberá priorizar soluciones que puedan ejecutarse con costos controlados.

## Componentes priorizados

| Componente | Estrategia de costo |
|---|---|
| React | Open source |
| Node.js | Open source |
| NestJS | Open source |
| Prisma | Uso de la versión adecuada al alcance del proyecto |
| PostgreSQL | Open source |
| OSRM | Priorizar despliegue/uso compatible con el presupuesto |
| PWA | Sin aplicación móvil nativa independiente |
| Hosting | Seleccionar una alternativa compatible con el presupuesto |
| Sistema operativo del servidor | Linux cuando sea viable |

La arquitectura evita, en la primera versión, desarrollar simultáneamente una aplicación Android/iOS nativa y una plataforma web independiente para el conductor.

# 10. Decisiones de Diseño Derivadas de las Restricciones

Las restricciones identificadas producen las siguientes decisiones arquitectónicas:

1. Se utilizará **PostgreSQL** como base de datos relacional.
2. El acceso a datos será gestionado mediante **Prisma**.
3. El backend será desarrollado con **NestJS sobre Node.js**.
4. El frontend será desarrollado con **React**.
5. El modo conductor utilizará una **PWA**, evitando una aplicación móvil nativa adicional en la primera versión.
6. OSRM será utilizado como servicio de información vial.
7. El Algoritmo Genético se ejecutará en el backend.
8. Las comunicaciones de producción deberán utilizar HTTPS.
9. Se aplicará control de acceso basado en roles.
10. La arquitectura priorizará tecnologías open source y servicios de infraestructura de bajo costo.
11. Los indicadores de sostenibilidad serán calculados y almacenados para las rutas generadas.
12. La plataforma deberá considerar escenarios de conectividad intermitente para el modo conductor.

---

# 11. Criterio de Cierre

Una restricción se considerará controlada cuando:

- Su impacto haya sido identificado.
- Exista una estrategia de mitigación documentada.
- La estrategia haya sido incorporada al diseño o backlog correspondiente.
- Exista una forma de verificar su cumplimiento.
- Los cambios que afecten la restricción sean registrados mediante el control de versiones Git.
