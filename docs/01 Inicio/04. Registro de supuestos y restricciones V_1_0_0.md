# 2. Propósito del documento

El presente documento registra los **supuestos y restricciones** identificados durante la fase de Inicio del proyecto.

Su propósito es establecer de manera explícita aquellas condiciones que se consideran verdaderas para planificar y ejecutar el proyecto, así como los factores limitantes que deberán respetarse durante su desarrollo.

El registro permitirá:

- Reducir ambigüedades durante la planificación.
- Identificar condiciones que necesitan validación.
- Anticipar impactos sobre alcance, tiempo, costo y tecnología.
- Facilitar la gestión de cambios.
- Mantener trazabilidad con el Acta de Constitución y la Declaración de la Visión.
- Servir como referencia para las fases posteriores del proyecto.

---

# 3. Contexto de referencia

El proyecto plantea desarrollar **EcoLogística Huancayo**, una plataforma web orientada a la optimización de rutas sostenibles de última milla mediante un **Algoritmo Genético**.

La solución contempla:

- Plataforma web responsive.
- Modo conductor mediante PWA.
- Gestión de pedidos.
- Gestión de vehículos.
- Gestión de conductores.
- Generación y optimización de rutas.
- Visualización cartográfica.
- Indicadores logísticos.
- Indicadores económicos.
- Indicadores ambientales.
- Re-optimización ante determinados eventos operativos.

La arquitectura tecnológica definida como línea base considera:

- **Frontend:** React + TypeScript.
- **Backend:** Node.js + NestJS.
- **Base de datos:** PostgreSQL + Prisma.
- **Mapas:** Leaflet + OpenStreetMap.
- **Ruteo:** OSRM.
- **Optimización:** Algoritmo Genético.
- **Acceso móvil:** PWA.

Estos elementos constituyen la línea base tecnológica inicial y podrán ser refinados durante las fases posteriores mediante el proceso de gestión de cambios correspondiente.

Las principales restricciones económicas son:

- Presupuesto limitado para el MVP.
- Necesidad de controlar servicios externos.
- Necesidad de seleccionar infraestructura compatible con el presupuesto.

- El alcance del MVP deberá mantenerse controlado.

- Los entregables documentales deberán mantener la nomenclatura solicitada.

# 9. Estrategia de gestión de supuestos

Los supuestos deberán administrarse de la siguiente manera:

```text
Identificar
    ↓
Registrar
    ↓
Clasificar impacto
    ↓
Definir validación
    ↓
Validar
    ↓
¿Se confirma?
 ┌──┴──┐
Sí    No
│      │
▼      ▼
Mantener   Convertir en
supuesto   riesgo / cambio
```

Cuando un supuesto resulte falso y tenga impacto significativo, deberá evaluarse como:

- Riesgo.
- Restricción.
- Cambio de alcance.
- Cambio técnico.
- Revisión de cronograma.

---

# 10. Estrategia de gestión de restricciones

Las restricciones deberán considerarse durante la toma de decisiones.

Cuando una restricción sea negociable, podrá evaluarse una alternativa siempre que:

1. Se documente el cambio.
2. Se analice su impacto.
3. Se obtenga la aprobación correspondiente.
4. Se actualicen los documentos afectados.

Las restricciones clasificadas como de baja flexibilidad no deberán modificarse sin una decisión formal del responsable correspondiente.

# 15. Línea base de control

Para la versión **1.0.0**, se establece como línea base que el proyecto:

- Se desarrollará en Huancayo.
- Utilizará una plataforma web como solución principal.
- Incorporará un modo conductor mediante PWA.
- Utilizará Node.js en el backend.
- Utilizará NestJS como framework backend.
- Utilizará React + TypeScript en el frontend.
- Utilizará PostgreSQL + Prisma para persistencia.
- Utilizará Leaflet + OpenStreetMap para visualización cartográfica.
- Utilizará OSRM como referencia inicial para ruteo.
- Utilizará un Algoritmo Genético para la optimización.
- Evaluará indicadores logísticos, económicos y ambientales.
- Mantendrá el alcance del MVP bajo control.

Estas condiciones constituyen una línea base inicial y cualquier modificación deberá gestionarse mediante el mecanismo de control de cambios definido para el proyecto.
