# 2. Propósito

Este documento identifica los perfiles que interactúan directa e indirectamente con la plataforma y define sus responsabilidades, necesidades de uso y permisos de acceso.

La clasificación se utiliza como base para:

- Definir las interacciones principales con el sistema.
- Establecer responsabilidades por perfil.
- Aplicar el principio de mínimo privilegio.
- Definir controles de acceso mediante RBAC.
- Mantener trazabilidad entre usuarios, requisitos funcionales y requisitos no funcionales.
- Servir como entrada para la elaboración posterior de casos de uso.

La línea base contempla los cuatro roles establecidos para la matriz de control de acceso:

1. **Administrador**
2. **Operador / Técnico**
3. **Usuario Final / Conductor**
4. **Auditor Externo**

# 4. Perfiles de Usuario

## 4.1 Administrador

### Objetivo

Administrar la configuración y operación general de la plataforma dentro de las autorizaciones establecidas.

### Necesidades

- Gestionar parámetros de configuración.
- Consultar información del sistema.
- Gestionar datos según sus permisos.
- Consultar registros de auditoría.
- Controlar los accesos asignados a los usuarios.

### Capacidades principales

- Configuración de parámetros.
- Gestión de datos transaccionales.
- Consulta de información.
- Revisión de registros de auditoría.
- Administración de permisos.

---

## 4.2 Operador / Técnico

### Objetivo

Gestionar las operaciones logísticas y la información necesaria para la planificación de rutas.

### Necesidades

- Registrar y actualizar pedidos.
- Registrar y actualizar información de la flota.
- Consultar rutas generadas.
- Gestionar operaciones permitidas.
- Consultar información necesaria para el seguimiento.

### Capacidades principales

- Registro y consulta de datos transaccionales.
- Gestión de pedidos.
- Gestión de flota.
- Consulta de rutas.
- Consulta de resultados de optimización.

---

## 4.3 Usuario Final / Conductor

### Objetivo

Ejecutar las entregas utilizando la información proporcionada por la plataforma.

### Necesidades

- Consultar la ruta asignada.
- Consultar entregas pendientes.
- Consultar información de cada entrega.
- Registrar el resultado de una entrega.
- Consultar alertas operativas disponibles.

### Capacidades principales

- Visualización de rutas.
- Consulta de entregas.
- Registro de resultados de entrega.
- Consulta de información operativa.

El conductor no tiene permisos para modificar parámetros de configuración ni eliminar físicamente información del sistema.

---

## 4.4 Auditor Externo

### Objetivo

Revisar información y registros autorizados para fines de control y auditoría.

### Necesidades

- Consultar información autorizada.
- Consultar registros de auditoría.
- Obtener evidencia de las operaciones realizadas.

### Capacidades principales

- Lectura de información autorizada.
- Lectura de logs de auditoría.
- Revisión de trazabilidad.

El auditor externo no modifica información transaccional ni realiza eliminación física de datos.

# 6. Matriz de Control de Acceso RBAC

La matriz aplica el modelo **RBAC (Role-Based Access Control)**. Los permisos se asignan al rol y no directamente a cada usuario.

### Convenciones

- **CRUD:** Crear, Leer, Actualizar y Eliminar.
- **C:** Crear.
- **R:** Leer / consultar.
- **U:** Actualizar.
- **D:** Eliminar.
- **Sin Acceso:** El rol no puede ejecutar la capacidad.

| Módulo / Capacidad | Administrador | Operador / Técnico | Usuario Final / Conductor | Auditor Externo |
|---|---|---|---|---|
| **Configuración de Parámetros** | **CRUD** | **R** | Sin Acceso | **R** |
| **Registro de Datos Transaccionales** | **CRUD** | **CRUD** | **C / R** | **R** |
| **Depuración / Eliminación Física** | **D** | Sin Acceso | Sin Acceso | Sin Acceso |
| **Exportación de Logs de Auditoría** | **R** | Sin Acceso | Sin Acceso | **R (Solo Lectura)** |

---

# 7. Matriz RBAC ampliada por capacidad

| Capacidad | Administrador | Operador / Técnico | Conductor | Auditor |
|---|---|---|---|---|
| Consultar información operativa | Sí | Sí | Sí, información asignada | Sí, información autorizada |
| Registrar información transaccional | Sí | Sí | Sí, resultado de entrega | No |
| Actualizar información transaccional | Sí | Sí | Según información asignada | No |
| Configurar parámetros | Sí | Solo lectura | No | Solo lectura |
| Generar / consultar rutas | Sí | Sí | Consulta ruta asignada | Consulta autorizada |
| Consultar logs de auditoría | Sí | No | No | Sí |
| Exportar logs de auditoría | Sí, lectura | No | No | Sí, solo lectura |
| Eliminación física | Sí | No | No | No |

> La matriz ampliada no sustituye la matriz RBAC oficial de la consigna; sirve para precisar la aplicación de los permisos a las capacidades del sistema.

# 8. Principios de Control de Acceso

## 8.1 Mínimo privilegio

Cada usuario deberá disponer únicamente de los permisos necesarios para ejecutar las actividades correspondientes a su rol.

## 8.2 Separación de funciones

Las funciones de operación, administración y auditoría deberán mantenerse diferenciadas para reducir el riesgo de modificaciones no autorizadas.

## 8.3 Trazabilidad

Las operaciones que requieran auditoría deberán poder relacionarse con el usuario que las ejecutó y con la operación realizada, de acuerdo con las capacidades definidas para el sistema.

## 8.4 Protección de datos

La información personal y operativa deberá estar disponible únicamente para los roles autorizados.

## 8.5 Control de acceso por rol

Los permisos se asignarán mediante roles definidos y no mediante autorizaciones informales.

# 12. Consideraciones sobre actores indirectos

Los actores indirectos forman parte del contexto del sistema, pero no necesariamente poseen una cuenta o permisos de acceso.

### Cliente

El cliente participa como fuente o receptor de información asociada al pedido. Su participación deberá limitarse a las funciones que posteriormente se definan en el alcance funcional.

### Servicios externos

Los servicios cartográficos o geográficos podrán intercambiar información con la plataforma. La integración concreta, autenticación y permisos de servicio serán especificados en la arquitectura.

---

# 13. Criterios para la evolución de perfiles

Los perfiles podrán modificarse únicamente cuando exista una necesidad funcional, normativa o de seguridad que lo justifique.

Cualquier nuevo rol deberá:

1. Tener una responsabilidad claramente definida.
2. Tener necesidades de uso identificadas.
3. Tener permisos diferenciados.
4. Mantener el principio de mínimo privilegio.
5. Mantener trazabilidad con los requisitos.
6. Ser incorporado mediante control de versión del documento.
