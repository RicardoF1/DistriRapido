## Persistencia y cierre

POST /auth/login conserva su respuesta JWT/identidad para compatibilidad con clientes Bearer y Swagger. Además establece `distrirapido_session`, cookie host-only (sin Domain), HttpOnly, SameSite=Lax, Path=/auth, con caducidad igual a la duración del JWT. Secure cuando FRONTEND_ORIGIN usa HTTPS o NODE_ENV=production; localhost HTTP requiere Secure=false. No se guardan contraseñas ni tokens en almacenamiento web, URLs o logs. React conserva únicamente identidad y fecha de expiración; descarta el JWT recibido como dato de sesión.

Al montar la aplicación, GET /auth/me con credentials=include valida firma, issuer, audience, caducidad obligatoria, usuario ACTIVO y rol vigente; devuelve la identidad y expiresAt absoluto en milisegundos Unix. Recargar no renueva la sesión ni amplía su caducidad. Las rutas esperan la comprobación, sin mostrar contenido protegido antes de validar. Un 401 vuelve al login; un fallo de red bloquea el acceso y ofrece reintento. También se comprueba la cookie al recuperar foco/visibilidad para detectar cierres en otra pestaña.

El botón visible “Cerrar sesión” ejecuta POST /auth/logout con cookies. La respuesta 204 elimina la cookie con los mismos atributos; después React elimina la identidad y redirige al login. Operación idempotente, disponible incluso con cookie ausente/expirada y sin bloqueo por límite de intentos de login. Un fallo de red conserva el estado actual y muestra error: el frontend no puede eliminar por sí mismo una cookie HttpOnly ni afirmar que se cerró sesión.

CORS acepta credenciales únicamente para FRONTEND_ORIGIN explícito. Login/logout rechazan orígenes ajenos y Fetch Metadata cross-site; se permite el propio origen de la API para Swagger. GET /auth/me mantiene compatibilidad Bearer (con precedencia si hay Authorization) y cookie. Su comprobación de identidad no se limita junto con los intentos de login.

La estrategia elimina la sesión disponible en el navegador; no revoca globalmente copias de un JWT exportado, que siguen válidas hasta expirar. Es una decisión mínima y explícita de MVP, sin lista de revocación, refresh tokens ni nuevos campos de negocio. No garantiza revocación de tokens robados. HttpOnly reduce exposición del token persistido, pero no sustituye prevención de XSS. Referencias: [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) y [cookies en NestJS](https://docs.nestjs.com/techniques/cookies).

## Prueba manual exacta

1. Mantener PostgreSQL actual en localhost:5433. No recrear el contenedor ni el volumen. No requiere migración ni volver a crear el administrador.
2. En la terminal del backend anterior, Ctrl+C. Desde backend: `npm run start:dev`. Es necesario reiniciarlo porque este comando no observa cambios. En este Windows, si el lanzador npm falla, usar `node 'C:\Program Files\nodejs\node_modules\npm\bin\npm-cli.js' run start:dev`.
3. Mantener/iniciar frontend desde frontend con `npm run dev` y abrir http://localhost:5173. Usar localhost tanto en frontend como API; no mezclar localhost y 127.0.0.1 para cookies.
4. Intentar contraseña incorrecta: debe aparecer el error de credenciales y permanecer en login.
5. Iniciar sesión con el administrador existente: /acceso/administrador y “Acceso permitido”.
6. Presionar F5: tras “Comprobando sesión…” debe continuar en /acceso/administrador, con la misma identidad.
7. Presionar “Cerrar sesión”: respuesta POST /auth/logout 204 y redirección /login. Cookie distrirapido_session eliminada.
8. Escribir directamente /acceso/administrador: vuelve a /login. F5 y botón Atrás tampoco restauran acceso.
9. Iniciar sesión otra vez y verificar GET /auth/me 200 en la pestaña Network. Tras logout, GET /auth/me sin Bearer debe devolver 401.
10. Para caducidad natural, esperar JWT_EXPIRES_IN vigente: se vuelve al login, también al recargar. Swagger sigue disponible en http://localhost:3000/api/docs; un Bearer exportado antes del logout conserva su vigencia hasta expirar, según la estrategia descrita.

Para reproducir E2E, usar exclusivamente un backend/base de pruebas con E2E_LOGIN_EMAIL, E2E_LOGIN_PASSWORD y JWT_SECRET del servidor de pruebas. No exponer esas variables. `npm run test:e2e` desde frontend. Integración: TEST_DATABASE_URL de una base aislada terminada en _test y `npm run test:integration` desde backend.
